Purpose of This Architecture
This architecture is designed to:
decouple email sending from payment processing
improve payment API responsiveness
avoid synchronous email bottlenecks
introduce buffering using RabbitMQ
improve reliability during traffic spikes
support asynchronous event-driven processing
This is a practical low-budget asynchronous architecture for startup/MVP-level payment systems.
Component Responsibilities
Component Responsibility
Spring Boot Backend Handles payment processing
n8n Webhook Receives payment events externally
RabbitMQ Buffers and queues messages
n8n Consumer WorkflowReads queue messages and processes email sending
Gmail SMTP Delivers emails to merchants/customers

What Is Burst Traffic?
Sudden spike in incoming events.
Example:
1000 payments in 10 seconds
How Architecture Handles Bursts
Backend
Backend remains stable because it only:
triggers webhook
does not wait for email send
RabbitMQ
Acts as shock absorber .
Stores incoming messages safely.
Consumer Workflow
Processes queue gradually.
Gmail
Becomes slowest component.

prevents data loss
supports retries
improves reliability
Duplicate Email Risk
Possible scenarios:

Possible result:

Use idempotency.
